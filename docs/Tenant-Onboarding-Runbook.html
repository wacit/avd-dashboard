1Server install (once per instance)

  1. Clone / copy the avd-dashboard folder to the management box.
  2. Run: 
    cd avd-dashboard
Copy-Item .env.example .env      # optional - only needed for agent key / port
.\run.ps1
  3. Set the agent ingest key in .env now if you plan to deploy the DEX agent (Phase 4): 
    AVD_AGENT_KEY=<long random string>    # e.g. a GUID + suffix
  4. Browse to http://127.0.0.1:8010/os. First boot shows No workspace linked and auto-opens the Connections app.
Security. The /api/connect/* endpoints are unauthenticated by design. Keep the app bound to 127.0.0.1 (default). If you must serve it remotely, front it with a reverse proxy that enforces authentication before exposing the port.

2Link the tenant (Connections app)

Option A — Device-code sign-in (recommended)

  1. In the Ops OS open 🔗 Connections (Start menu or desktop icon).
  2. Enter the customer Tenant ID (optional but recommended), click Sign in with device code.
  3. The window shows a one-time code. Go to https://microsoft.com/devicelogin, enter the code, and sign in with the onboarding identity from Phase 0.
  4. The app polls automatically and flips to Linked tenant when sign-in completes. Tokens are cached (DPAPI on Windows) — restarts are silent, no re-auth.

Option B — Service principal

  1. Entra admin center → App registrations → New registration (e.g. avd-dex-dashboard), single tenant. No redirect URI needed.
  2. Create a client secret (Certificates & secrets) and note tenant ID / client (app) ID / secret value.
  3. Assign RBAC (Azure portal, not Entra):
    • Log Analytics Reader on the workspace (or its resource group)
    • Reader on the subscription — needed for workspace discovery
  4. In Connections expand Use a service principal instead, enter the three values, click Connect service principal. The backend validates against Entra before saving (stored in connection.json on the server — treat that file as a secret).

3Pick the workspace

  1. After linking, the Workspace dropdown appears and lists every Log Analytics workspace the identity can see, grouped subscription / resource-group / name.
  2. Select the workspace that AVD Insights writes to and click Use selected workspace.
  3. Data loads immediately — the DEX score pill in the tray goes live within one refresh (60 s max, or click Refresh in Settings).
Tip. If the list is empty the identity lacks Reader on the subscription. You can still link manually: set AVD_WORKSPACE_ID=<workspace GUID> in .env and restart — the linked credential is still used for queries.

4Deploy the DEX agent to session hosts

Without the agent the score uses Log Analytics factors only. The agent adds input delay, FPS, packet loss, UDP/Shortpath use, idle & disconnected session tracking, app crashes/hangs and FSLogix load times.

  1. Copy the agent\ folder to a session host (or push via Intune / Nerdio scripted action / GPO startup script).
  2. Run as admin on each host: 
    .\Install-AvdDexAgent.ps1 `
    -ServerUrl "http://<dashboard-host>:8010" `
    -ApiKey    "<AVD_AGENT_KEY from Phase 1>" `
    -HostPool  "<host pool name>"       # optional but enables pool filtering
  3. The installer registers scheduled task AvdDexAgent (SYSTEM, every minute). Offline samples spool to disk and back-fill when the server is reachable.
  4. Verify from the server: GET /api/agent/status → hosts_reporting > 0, or watch the note in the Agent Telemetry app turn into a feed status line.
Image-based pools. For golden-image environments bake the install into the image (or run the installer via Nerdio scripted action on provision) so re-imaged hosts keep reporting.

5Verify

  • Connections shows Linked tenant + the chosen workspace name.
  • Tray pill shows a numeric DEX score (not "DEX —").
  • Experience Score app shows factor bars sourced from logs (and agent after Phase 4).
  • User Experience / Host Experience windows list rows for the selected range.
  • Logon Waterfall shows checkpoint milestones.
  • Agent Telemetry shows hosts reporting (if Phase 4 done).
  • No red warnings in the classic dashboard banner (/) other than optional tables you skipped (e.g. graphics preview).

Multiple tenants

Each instance holds one linked tenant (connection.json + token cache are per-folder). To monitor several tenants side by side:

TenantFolderPortURL
Tenant Aavd-dashboard-tenantA8010http://127.0.0.1:8010/os
Tenant Bavd-dashboard-tenantB8011http://127.0.0.1:8011/os
Tenant Cavd-dashboard-tenantC8012http://127.0.0.1:8012/os

Copy the project folder per tenant, set AVD_APP_PORT (and a unique AVD_AGENT_KEY) in each .env, then run this runbook's Phases 2–5 in each instance. Switching a single instance to a different tenant is just Disconnect → link again.

Troubleshooting

SymptomLikely cause → fix
Device code fails with AADSTS500113 / consent errorTenant blocks public-client/Azure CLI consent → use service principal (Phase 2B).
AADSTS50076 / MFA loopConditional Access requires compliant device → sign in from an allowed device or use SP.
Workspace dropdown emptyIdentity lacks Reader on subscriptions → assign Reader, click ↻. Or set AVD_WORKSPACE_ID manually.
Panels show "table may not exist"AVD Insights not onboarded / DCR missing that table → fix Insights config; optional tables (graphics preview) can be ignored.
Score shows but users/hosts emptySelected range has no connections → widen the range; confirm host pool filter.
Agent ingest returns 503AVD_AGENT_KEY not set on the server → set it in .env, restart.
Agent ingest returns 401Key mismatch → re-run installer with the server's key.
No input-delay dataCounter requires Win10/Server 2019+ and an active session; instance appears only while users are logged on.
Queries fail after re-linkingStale token cache → Disconnect, then link again; check server log for the credential error.

Printable checklist (per tenant)

  • Phase 0: AVD Insights tables flowing; onboarding identity has Log Analytics Reader + Reader; Tenant ID recorded
  • Phase 1: Instance folder + port assigned; AVD_AGENT_KEY generated
  • Phase 2: Tenant linked (device code or SP) — Connections shows account + tenant
  • Phase 3: Workspace selected; data loading
  • Phase 4: DEX agent deployed to all session hosts; hosts_reporting matches host count
  • Phase 5: Verification list all green; handover URL shared with the customer admin
